# Mini Task Tracker

A small task tracker built for the MERN technical assignment. It supports creating tasks, listing and filtering tasks by status, updating task status, and deleting tasks after confirmation.

## Technology
- React + TypeScript (frontend)
- Node.js + Express (REST API)
- MongoDB + Mongoose (persistence)
- Jest + Supertest + mongodb-memory-server (API tests)

## Database assumption
The assignment's opening line mentions PostgreSQL, while its explicit persistence requirement says MongoDB. This implementation follows the explicit requirement to persist data in MongoDB. No PostgreSQL database is used.

## Requirements
- Node.js 18 or newer
- MongoDB running locally, or a MongoDB connection URI

## Setup

### 1. Start the backend
```bash
cd backend
npm install
cp .env.example .env
```
Set `MONGODB_URI` in `backend/.env` to your MongoDB URI. Then run:
```bash
npm run dev
```
The API runs at `http://localhost:5000` by default.

### 2. Start the frontend
Open a second terminal:
```bash
cd frontend
npm install
npm run dev
```
Open the local URL printed by Vite (normally `http://localhost:5173`). The frontend uses `http://localhost:5000` by default. To use a different API URL, create `frontend/.env` with `VITE_API_URL=http://localhost:5000`.

### 3. Run backend tests
```bash
cd backend
npm test
```
The tests use an in-memory MongoDB instance and do not require the local MongoDB server. The first run may need internet access to download the MongoDB test binary.

## API
- `POST /tasks` — create a task. Body: `{ "title": "...", "description": "optional", "status": "To Do", "priority": "Medium" }`
- `GET /tasks` — list tasks. Optional query: `?status=To%20Do`, `?status=In%20Progress`, or `?status=Done`.
- `PATCH /tasks/:id` — update status. Body: `{ "status": "Done" }`.
- `DELETE /tasks/:id` — delete a task.

Allowed statuses: `To Do`, `In Progress`, `Done`. Allowed priorities: `Low`, `Medium`, `High`. Title is required and limited to 100 characters. Status and priority default to `To Do` and `Medium` if omitted. `createdAt` is generated by the database model.

## Tests included
1. Reject task creation when title is missing and verify that no task is stored.
2. Update a stored task's status successfully and verify the persisted value.

## Authentication and production access restrictions
Authentication is outside this assignment's scope. For production, add an authentication flow and issue a securely managed session or signed token after login. Hash passwords with a password-hashing algorithm such as Argon2 or bcrypt. Protect task endpoints with authentication middleware and scope every task query/update/delete to the authenticated user's ID, so one user cannot access another user's tasks. Validate authorization on the server rather than relying on frontend controls.

## Technical decisions, assumptions, limitations
- Followed the explicit MongoDB persistence requirement despite the conflicting PostgreSQL mention in the opening line.
- Status is the only editable task field because the required update API is specifically for task status.
- No authentication or cloud deployment was added, as requested by the assignment scope.
- Improvements with more time: add broader API/UI test coverage and automated linting. No additional product features are included.
